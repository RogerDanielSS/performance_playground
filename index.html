Layout Comparison

Tables & floats vs modern CSS Grid — identical product data, very different behavior.

BAD

Fixed-width <table> + floats

The table below is hard-coded to 720px. On phones it overflows (try shrinking the window), and the old float hack needs clearfix hacks and breaks with uneven heights.

Product Price Rating

layout-bad.css
/* BAD — <table> with fixed px */
table.products {
  width: 720px;          /* never adapts */
  table-layout: fixed;
  font-size: 15px;       /* fixed type */
}
/* …or the float hack */
.col { float: left; width: 33.33%; }
/* no media queries, no wrapping →
   broken on small screens */
  • Fixed widths overflow small viewports; users must scroll horizontally.
  • float removes items from normal flow — clearfix hacks and collapsed heights.
  • Every breakpoint needs another hand-written override → CSS bloat.
Why it matters

Rigid layouts force the browser to reflow the whole table whenever content or viewport changes, and they alienate the ~60% of traffic on mobile.

GOOD

CSS Grid — auto-fit + minmax()

One line of Grid does the whole responsive job: as many 250px-minimum columns as fit, then leftover space is shared. No media queries required for the grid itself.

layout-good.css
/* GOOD — responsive by default */
.product-grid {
  display: grid;
  grid-template-columns:
    repeat(auto-fit, minmax(250px, 1fr));
  gap: clamp(10px, 1.6vw, 18px);
}
.product-card { transition: transform .2s; }
.product-card:hover { transform: translateY(-4px); }
/* transform hover = composite only */
  • auto-fit wraps items automatically — 1 column on a phone, 4 on a desktop.
  • minmax(250px, 1fr) guarantees a usable minimum and fair space distribution.
  • Hover effects use transform — compositor-only, zero reflow.
Why it matters

Grid keeps layout calculations minimal and predictable. Pages adapt to any screen with a few declarations instead of a pile of media queries.

Two navigation bars inside live "viewport" frames. Resize the window — a ResizeObserver updates the readouts below each frame.

BAD

Fixed pixel nav

Hard-coded 720px min-width, nowrap links, fixed 15px type. Below 720px the bar is simply clipped.

nav-bad.css
/* BAD — fixed pixels everywhere */
.nav { width: 720px; font-size: 15px; }
.nav a {
  display: inline-block;
  padding: 0 18px;
  white-space: nowrap;
}
/* no media queries → breaks */
Why it matters

Pixel-fixed components can't adapt to any viewport you didn't predict. Combined with desktop-first CSS, mobile users pay the price.

GOOD

Flexbox + clamp() + mobile-first

Flexbox with flex-wrap, fluid type via clamp(), and a mobile-first min-width query that enhances rather than patches.

Viewport width — px mobile
Home Products Pricing Blog About Sign up
nav-good.css
/* GOOD — mobile-first flexbox */
.nav {
  display: flex;
  flex-direction: column;      /* base: stacked */
  gap: clamp(6px, 1.2vw, 14px);
}
.nav__link {
  font-size: clamp(0.9rem, 0.82rem + 0.5vw, 1.05rem);
}
@media (min-width: 640px) {
  .nav { flex-direction: row; flex-wrap: wrap; }
}
  • clamp() keeps type readable at every size without a single extra query.
  • Mobile-first min-width queries only ever add layout — no fighting an inherited desktop layout.
  • Flexbox lays out siblings in one pass — no absolute positioning, no clearfix.
Why it matters

Fluid components survive any future screen size (foldables, ultrawide, split-view) with zero maintenance. That's what "responsive" actually means.

Animation Performance

Both orbs are driven by requestAnimationFrame. One invalidates layout every frame; the other only touches the compositor.

BAD

Animating left / top

Each frame writes left/top and then forces a synchronous layout read (offsetLeft). That read cannot be deferred: the browser must run Style → Layout → Paint → Composite on every single frame.

BAD
FPS—
Frame time—
Forced layout reads0
Layout shifts (position deltas)0
ResizeObserver fires0

RO never fires here — it only watches size, so positional reflows stay invisible to it.

anim-bad.css
/* BAD — animates layout properties */
@keyframes drift {
  from { left: 0; top: 0; }
  to   { left: 140px; top: 90px; }
}
.orb { position: absolute; left: 0; top: 0; }
/* left/top → Style + Layout + Paint
   + Composite, every frame */
Why it matters

Layout is the most expensive stage of the pipeline. Animating left/top reflows the document 60× per second — jank on mid-range phones, and the main thread blocks everything else.

GOOD

Animating transform + opacity

transform and opacity are handled by the compositor thread: no layout, no paint. The orb is promoted to its own layer (will-change) and just glides.

GOOD
FPS—
Frame time—
Forced layout reads0

Zero reads, zero writes to layout properties. The main thread stays free.

anim-good.css
/* GOOD — compositor-only properties */
.orb {
  transform: translate3d(0, 0, 0);
  opacity: 1;
  will-change: transform;   /* layer hint */
}
/* transform + opacity skip
   Layout & Paint → Composite */
  • transform/opacity run off the main thread — 60fps even while JS is busy.
  • will-change is a hint, used only for elements that will actually animate.
Style → Layout → Paint → Composite
Why it matters

Compositor-only animations keep the main thread free for input and JS. That's the difference between a "smooth 60fps" product and a janky one.

DOM Manipulation

Same work, different technique. Each button appends 100 items and reports elapsed time, forced reads and style writes.

One-by-one appends

    Ready — 100 items

    DocumentFragment batch

      Ready — 100 items

      dom-bad.js vs dom-good.js
      // BAD — 100 appends, 100 forced reflows
for (let i = 0; i < 100; i++) {
  const li = document.createElement('li');
  li.textContent = 'Item ' + i;
  list.appendChild(li);   // invalidates layout
  void list.offsetHeight; // forced reflow
}

// GOOD — build off-DOM, insert once
const frag = document.createDocumentFragment();
for (let i = 0; i < 100; i++) {
  const li = document.createElement('li');
  li.textContent = 'Item ' + i;
  frag.appendChild(li);   // no layout work
}
list.appendChild(frag);   // one reflow total

      Bonus: Layout Thrashing

      Interleaving reads (e.g. offsetWidth) with writes (e.g. style.width) forces the browser to reflow on every read — the classic read-write ping-pong. The fix: batch all reads first, then write.

      Click a loop to measure it.

      Why it matters

      Each forced reflow can cost 1–5ms. A 100-item loop with reads costs hundreds of ms of main-thread time — exactly what DocumentFragment and read/write batching eliminate.

      Network & Caching

      Rendering doesn't start at parse — it starts at the network. Below: the conceptual request flow, then a live lazy-loading demo.

      BAD

      No cache headers

      Without Cache-Control, the browser re-downloads everything on every visit — even byte-identical files.

      Every single visit
      GET /app.css200 OK · 21 KB
      ↓
      GET /app.js200 OK · 48 KB
      ↓
      GET /logo.png200 OK · 9 KB
      ↓
      GET /font.woff2200 OK · 32 KB
      response headers
      # no cache headers present
GET /app.css  200 OK  (21 KB)   ← every visit
GET /app.js   200 OK  (48 KB)   ← every visit
      Why it matters

      Re-downloading static assets multiplies load time, battery drain and server cost — and it's trivially avoidable.

      GOOD

      Immutable cache + cache-busting

      Hash-busted filenames (app.a1b2c3.css) make content immutable: the browser fetches once, then serves from cache forever. Deploys change the hash → new file.

      First visit
      GET /app.a1b2c3.css200 OK
      ↓ cached with immutable
      GET /app.a1b2c3.cssfrom cache · 0 ms
      ↓ next deploy → new hash
      GET /app.f4e5d6.cssfrom cache · 0 ms
      ↓
      GET /api/config304 Not Modified
      response headers
      Cache-Control: public, max-age=31536000, immutable
# hash-busted filenames = permanent cache
app.a1b2c3.css  200 OK      (first visit)
app.a1b2c3.css  from cache  (subsequent)
      Why it matters

      Repeat visits become near-instant: the HTML round-trip is the only network cost. That's the fastest "performance optimization" there is.
